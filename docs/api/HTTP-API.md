# Whitebase HTTP API

Whitebase Server exposes a local HTTP/JSON API for running Whitebase computations from a browser or another local client.

> [!IMPORTANT]
> Whitebase is an experimental repository. The API and response formats may change as operations and backends are added.

## Base URL

```text
http://127.0.0.1:1430
```

The current server binds to the loopback interface only.

Start it from the repository root:

```powershell
cargo run -p whitebase-server
```

## Endpoint Summary

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/health` | Check whether Whitebase Server is running. |
| `POST` | `/api/observations/add-scalar-f64` | Observe scalar `f64` addition, including decimal and bit representations. |
| `POST` | `/api/benchmarks/run` | Run a benchmark by operation and precision. |
| `POST` | `/api/benchmarks/add-array` | Compatibility endpoint for array addition. |
| `POST` | `/api/benchmarks/add-f32` | Legacy endpoint for `f32` array addition. |

## CORS

The server currently allows browser requests from:

- `http://localhost:1420`
- `http://127.0.0.1:1420`
- `https://hokutaka.github.io`

Allowed methods are `GET` and `POST`, and `Content-Type` is an allowed request header.

## Health Check

### `GET /api/health`

Example:

```powershell
Invoke-RestMethod `
  -Uri "http://127.0.0.1:1430/api/health"
```

Response:

```json
{
  "status": "ok",
  "service": "whitebase-server"
}
```

## Benchmark API

### `POST /api/benchmarks/run`

This is the primary benchmark endpoint.

The server generates benchmark input internally, runs the selected operation through Whitebase Runner, compares available backends against the reference result, and returns timing and comparison data.

### Request

```json
{
  "operation": "sum-f64",
  "precision": "f64",
  "inputLength": 1000000,
  "warmupIterations": 10,
  "measuredIterations": 100
}
```

| Field | Type | Required | Values / limits | Description |
| --- | --- | ---: | --- | --- |
| `operation` | string | No | `add-array`, `sum-f64` | Operation to benchmark. Defaults to `add-array` when omitted. |
| `precision` | string | Yes | `f32`, `f64` | Floating-point precision. |
| `inputLength` | integer | Yes | `1..=10,000,000` | Number of generated input elements. |
| `warmupIterations` | integer | Yes | `0..=10,000` | Warm-up iterations before measurement. |
| `measuredIterations` | integer | Yes | `1..=10,000` | Number of measured iterations. |

Supported operation/precision combinations:

| Operation | `f32` | `f64` |
| --- | ---: | ---: |
| `add-array` | Supported | Supported |
| `sum-f64` | Not supported | Supported |

A `sum-f64` request with `precision: "f32"` returns HTTP `400` with error code `invalid_benchmark_precision`.

### Generated Inputs

Benchmark arrays are generated by the server rather than supplied by the request.

For array addition, the server generates both left-hand and right-hand arrays. For `sum-f64`, it generates the same `f64` left-hand input used by the `f64` array benchmark and reduces that array to a single sum.

### Response

Timing values are expressed in nanoseconds.

The exact backend list depends on the platform and backend availability.

```json
{
  "operation": "sum-f64",
  "precision": "f64",
  "inputLength": 1000000,
  "referenceBackend": "<reference backend>",
  "warmupIterations": 10,
  "measuredIterations": 100,
  "absoluteTolerance": 1e-12,
  "results": [
    {
      "backend": "<backend display name>",
      "status": "completed",
      "timingStatus": "measured",
      "iterations": 100,
      "totalNanoseconds": 1234567,
      "minimumNanoseconds": 12000,
      "maximumNanoseconds": 13000,
      "meanNanoseconds": 12345.67,
      "matchesReference": true,
      "mismatchCount": 0,
      "maximumAbsoluteError": 0.0,
      "error": null
    }
  ]
}
```

The numeric timing values above are illustrative only. Real results depend on the build configuration, CPU, cache, memory bandwidth, operating-system scheduling, and other environmental factors.

### Backend Result Status

Each item in `results` has one of the following statuses.

| Status | Meaning |
| --- | --- |
| `completed` | The backend ran successfully. Comparison fields are populated. Timing fields depend on `timingStatus`. |
| `unavailable` | The backend is not available on the current platform or CPU. Timing and comparison fields are `null`. |
| `failed` | The backend was available but execution failed. The `error` field contains the failure message. |

### Timing Status

A completed backend result has one of the following `timingStatus` values.

| Timing status | Meaning |
| --- | --- |
| `measured` | Every measured iteration produced an observable execution time. |
| `too-fast-to-measure` | One or more measured iterations were below the current timer resolution. |

When `timingStatus` is `too-fast-to-measure`, the backend status remains
`completed`. The computation and reference comparison are still valid, but the
timing values are not reported and the result is excluded from fastest and
speedup calculations.

In this state, `iterations`, `totalNanoseconds`, `minimumNanoseconds`,
`maximumNanoseconds`, and `meanNanoseconds` are `null`.

For a completed result:

- `matchesReference` indicates whether the result matched the reference under the configured tolerance.
- `mismatchCount` is the number of mismatching result elements or values reported by Runner.
- `maximumAbsoluteError` is the maximum absolute difference observed. It may be `null` when no finite value can be reported.

### PowerShell: `sum-f64`

```powershell
$body = @{
  operation = "sum-f64"
  precision = "f64"
  inputLength = 1000000
  warmupIterations = 10
  measuredIterations = 100
} | ConvertTo-Json

Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:1430/api/benchmarks/run" `
  -ContentType "application/json" `
  -Body $body
```

## Compatibility Benchmark Endpoints

### `POST /api/benchmarks/add-array`

This endpoint uses the same benchmark request format as `/api/benchmarks/run`, but the server always executes `add-array`.

If an `operation` value is supplied, it is ignored and replaced with `add-array`.

Example:

```json
{
  "precision": "f64",
  "inputLength": 1000000,
  "warmupIterations": 10,
  "measuredIterations": 100
}
```

### `POST /api/benchmarks/add-f32`

This is the legacy `f32` array-addition endpoint.

It accepts only the benchmark sizing fields:

```json
{
  "inputLength": 1000000,
  "warmupIterations": 10,
  "measuredIterations": 100
}
```

The server executes the request as:

```text
operation = add-array
precision = f32
```

New clients should prefer `/api/benchmarks/run`.

## Scalar `f64` Observation API

### `POST /api/observations/add-scalar-f64`

This endpoint is intended for observing scalar IEEE 754 `f64` addition across available backends.

Unlike the benchmark endpoint, `lhs` and `rhs` are decimal strings supplied by the client.

Request:

```json
{
  "lhs": "0.1",
  "rhs": "0.2"
}
```

Response fields include:

| Field | Description |
| --- | --- |
| `lhsInput` | Original left-hand decimal string. |
| `rhsInput` | Original right-hand decimal string. |
| `lhs` | Parsed `f64` value, decimal rendering, and bit pattern. |
| `rhs` | Parsed `f64` value, decimal rendering, and bit pattern. |
| `decimalReference` | Decimal reference result calculated by Runner. |
| `reference` | Reference `f64` value, decimal rendering, and bit pattern. |
| `results` | Per-backend result and bitwise comparison. |
| `allBackendsMatch` | Whether all reported backend results match the reference bits. |

`lhs`, `rhs`, `reference`, and each backend `result` use this shape:

```json
{
  "value": 0.3,
  "decimal": "0.29999999999999999",
  "bits": "0x3fd3333333333333"
}
```

Each backend observation uses this shape:

```json
{
  "backend": "<backend display name>",
  "result": {
    "value": 0.3,
    "decimal": "0.29999999999999999",
    "bits": "0x3fd3333333333333"
  },
  "matchesReferenceBits": true
}
```

PowerShell example:

```powershell
$body = @{
  lhs = "0.1"
  rhs = "0.2"
} | ConvertTo-Json

Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:1430/api/observations/add-scalar-f64" `
  -ContentType "application/json" `
  -Body $body
```

## Errors

API errors use this JSON shape:

```json
{
  "code": "input_length_zero",
  "message": "input length must be greater than zero"
}
```

Benchmark validation errors currently include:

| HTTP status | Code | Condition |
| ---: | --- | --- |
| `400` | `input_length_zero` | `inputLength` is `0`. |
| `400` | `input_length_too_large` | `inputLength` exceeds `10,000,000`. |
| `400` | `measured_iterations_zero` | `measuredIterations` is `0`. |
| `400` | `warmup_iterations_too_large` | `warmupIterations` exceeds `10,000`. |
| `400` | `measured_iterations_too_large` | `measuredIterations` exceeds `10,000`. |
| `400` | `invalid_benchmark_precision` | `sum-f64` is requested with a precision other than `f64`. |

The scalar observation endpoint returns `400` with `invalid_scalar_f64_request` for invalid scalar input or an out-of-range reference.

Execution or background-task failures are returned as HTTP `500` errors with an error `code` and `message`.

## Notes

- The server currently listens on `127.0.0.1:1430`; it is not exposed on all network interfaces.
- The current server does not define an authentication layer.
- `/api/benchmarks/run` is the preferred benchmark endpoint for new clients.
- Benchmark results should be compared using Release builds when performance is the subject of the experiment.
